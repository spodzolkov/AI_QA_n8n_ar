# Правила проєкту: Multi-Harness n8n Flow Architect

Цей робочий простір призначений для проєктування, створення та модифікації воркфлоу **n8n** на основі текстових і табличних документів-інструкцій (посилання на Google Docs, `.docx`, `.doc`, `.md`, `.txt`) з подальшим інтерактивним уточненням вимог прямо в агентському чаті.

## Основні засади роботи агента

1. **Використовуйте підключені MCP-сервери**:
   - **`doc-ingest`**: використовуйте `read_instruction_document` для читання будь-яких документів-інструкцій (Google Docs URL, `.docx`, `.doc`, `.md`, `.txt`), `list_local_instruction_files` для огляду папки `user-docs/` та `check_n8n_health` для перевірки зв'язку з інстансом n8n і перегляду фактично підтримуваних `typeVersion` нод на сервері.
   - **`n8n-mcp`**: використовуйте інструменти бази нод (пошук нод, отримання схем параметрів та валідацію) **перед** формуванням JSON воркфлоу, а також інструменти CRUD управління воркфлоу для прямого створення/оновлення флоу на сервері n8n.
   - Якщо з якоїсь причини MCP-сервер ще не перезавантажений у поточній сесії після `/init`, ви можете зчитати документ командою `npm run parse-doc -- "<джерело>"` і підказати користувачу оновити підключення MCP.

2. **Двоетапний діалог та побудова флоу**:
   - Дотримуйтеся скіла `n8n-flow-builder`:
     1) Спочатку зчитайте документ і перевірте критичні блокери (якщо документ недоступний, сервер n8n не відповідає або незрозуміло який існуючий флоу модифікувати — поставте короткі критичні питання перед стартом).
     2) Побудуйте або оновіть валідну чернетку флоу в n8n (`active: false`), розмістивши `Sticky Note` ноди біля місць, які потребують Credentials чи уточнень.
     3) Надайте посилання на створений/оновлений флоу і **обов'язково поставте структуровані уточнюючі питання в агентському чаті** (Credentials, умови розгалуження, мапінг полів, обробка помилок), після чого ітеративно оновлюйте флоу на основі відповідей користувача.

3. **Захист приватності та чистота Git-репозиторію**:
   - **Ніколи** не записуйте реальні API-ключі, токени або паролі прямо у параметри нод воркфлоу чи у відстежувані Git-файли. Секрети проєкту зберігаються виключно у `.env`.
   - Для збереження або оновлення чистого шаблону проєкту на GitHub використовуйте `npm run check:clean` (сканер відсутності користувацьких даних) та `npm run github:publish`.

## Технічні запобіжники та обходи відомих проблем n8n / MCP

1. **Сумісність `typeVersion` нод із реальною версією сервера n8n**:
   - База схем `n8n-mcp` (`latest`) може пропонувати новіші `typeVersion`, ніж підтримує запущений контейнер n8n користувача. Якщо у JSON воркфлоу стоїть вища `typeVersion`, ніж знає фронтенд n8n, при відкритті й збереженні флоу у браузері редактор скидає `parameters` такої ноди у порожній об'єкт `{}` (наприклад, помилка `Parameter "Fields To Split Out" is required`).
   - Завжди звіряйте `typeVersion` із `observedNodeTypeVersions` із `check_n8n_health` або наявними воркфлоу на сервері. Зокрема: для `n8n-nodes-base.splitOut` використовуйте сумісну **`typeVersion: 1`** (не `1.1`, якщо `1.1` явно не присутня на сервері), для `n8n-nodes-base.switch` — **`typeVersion: 3.4`** (із `conditions.options.version: 3`).
2. **Обов'язкова звірка живих Credentials (`n8n_manage_credentials`)**:
   - При клонуванні або модифікації існуючого воркфлоу **ніколи** не копіюйте старі `credentials.<type>.id` наосліп — користувач міг перестворити обліковий запис, і старий ID викличе помилку `Credential with ID "..." does not exist`. Завжди викликайте `n8n_manage_credentials({ action: "list" })` та підв'язуйте актуальні чинні ID.
3. **Порядок вихідних портів у `SplitInBatches v3` (`Loop Over Items`)**:
   - У `n8n-nodes-base.splitInBatches` (`typeVersion: 3`) індекси портів зворотні до інтуїтивних: **`main[0]` (індекс 0) = `done`** (після завершення циклу), а **`main[1]` (індекс 1) = `loop`** (тіло циклу, яке обов'язково замикається назад на вхід `SplitInBatches`). Завжди явно задавайте `batchSize` у `parameters`.
4. **Префікс `=` у змішаних та HTML/Markdown виразах**:
   - У JSON воркфлоу всі поля з підстановками `{{ ... }}` (включно з `formFields.values[].html` у `n8n-nodes-base.form` та `markdown` у `n8n-nodes-base.notion`) обов'язково повинні починатися зі знака `=` (`"=<h3>{{ ... }}</h3>"`). Також перевіряйте, щоб URL-поля не містили зайвих кутових дужок `<https://...>`, скопійованих із документації.
5. **Захист від пошкоджених формул у Google Docs / `.docx`**:
   - Якщо документ-інструкція містить два символи `$` в одному абзаці (наприклад, `$('Node A') ... $('Node B')`), редактор Google Docs може перетворити фрагмент між ними на формулу `<m:oMath>`, а символ `||` усередині Markdown-таблиці може обрізати решту виразу в комірці. Парсер `doc-ingest` автоматично відновлює `<m:oMath>` із `.docx`, але агент завжди повинен перевіряти синтаксичну цілісність JS-виразів перед записом у ноди.
6. **Послідовна валідація в `n8n-mcp` та оновлення вкладки браузера (`F5`)**:
   - Виконуйте важкі виклики `validate_workflow` / `n8n_validate_workflow` послідовно (не запускайте кілька одночасно в один stdio-процес).
   - Після кожного програмного оновлення існуючого воркфлоу через API обов'язково нагадуйте користувачу **оновити сторінку воркфлоу у браузері (`F5`) перед натисканням *Save***, щоб старий стан відкритої вкладки не перезаписав оновлені параметри нод.
